## 0. 先回答一个关键问题：以后换成圆形屏怎么办？

**这是本规格的第一节，因为它决定了后面所有内容怎么写。**

### 0.1 影响有多大：分三层，影响完全不同

| 层 | 换圆形屏的影响 | 说明 |
|---|---|---|
| **数据契约**（每屏要哪些字段） | **零影响** | 黄历还是那几个字段，今日还是那几句话 |
| **业务逻辑**（黄历计算、缓存、授权） | **零影响** | 和内接矩形屏幕的形状无关 |
| **布局层**（每屏怎么排） | **要重做** | 这是唯一受影响的部分 |

**结论：如果一开始就把「布局」和「数据」分开写，换屏幕形状只需要重写布局层，
大约是一两天的活，不是重做项目。**

本规格就是按这个原则写的——见 §4 的分层结构。

### 0.2 但圆形屏有两个必须提前知道的代价

**代价一：边角没了（这是主要问题）**

圆形的**总面积**其实不小——直径 480 的圆占同样 480×480 矩形的 **78.5%**：

| | 面积 |
|---|---|
| 矩形 480×480 | 230,400 |
| 圆形 直径 480 | 180,956（**78.5%**） |

**真正的问题不是面积，而是形状**：圆没有"角落"，越靠边的内容越被切掉。

| 我们现在的设计 | 在圆形屏上 |
|---|---|
| 状态行（时间、电量）放左上/右上角 | **角落不存在，会被切掉** |
| 黄历的「宜 / 忌」多行列表 | **靠边的行会被圆形切掉**，读不全 |
| 四角对齐的排版 | 完全失效，必须改成居中 / 径向布局 |
| 顶部对齐的大标题 | 需要下移，进入"安全区" |

**代价二：有效宽度缩水**

圆形屏要留安全区（内容不贴边），经验值是**直径的 70%**：
480 的圆，安全区约 **336 × 336**。

按我们之前算的字号规则：

| | 一行能放几个字（28px） |
|---|---|
| 矩形 480 | **17 字** |
| 圆形 480（安全区 336） | **12 字** |

也就是说：**内容容量大约只剩七成**，而多行列表的损失更大（边缘行会被切）。

### 0.3 由此带来的产品影响（这个比技术影响更重要）

**圆形屏放不下「黄历列表」，所以待机页必须重新设计。**

黄历天然是"多行清单"（宜 3 条、忌 3 条、方位、冲煞），
而圆形屏最不擅长的就是多行清单——**越靠边的行越被切掉**。

圆形屏擅长的反而是另一种表达：

| 圆形屏适合 | 圆形屏不适合 |
|---|---|
| 一个中心大字（今天的"平"） | 多行列表 |
| 一圈刻度 / 进度环（今日能量高低） | 表格化信息 |
| 一句话居中 | 左右分栏 |
| 时辰环（12 时辰绕一圈） | 状态栏在角落 |

**所以如果最终决定做圆形屏，产品的信息架构要从"黄历卡片"改成"一个念头的物件"**：
中心一个大字 + 一句短句 + 一圈环。这其实是更像"陪伴物"的形态，
但**黄历那部分价值会大幅缩水**（可能只剩农历日 + 一个节气）。

> 一句话：**换圆形屏不是换个壳，是把产品从"信息卡片"变成"一个符号"。**
> 这个取舍建议主导人早点定。

### 0.4 我的建议：怎么做才能两种都留得住

**做法：把布局参数抽成配置，一个开关切换。**

```c
// layout_config.h（示意，实际随实现调整）
typedef struct {
    uint16_t width;         // 480
    uint16_t height;        // 480
    uint8_t  corner_radius; // 0 = 矩形；240 = 圆形（半径）
    uint16_t safe_w;        // 安全区宽：矩形 480 / 圆形 336
    uint16_t safe_h;        // 安全区高
    uint16_t pad;           // 边距：矩形 32 / 圆形按半径算
    uint8_t  max_chars;     // 单行最大字数（由 safe_w 和字号算出）
} screen_layout_t;

extern const screen_layout_t LAYOUT_RECT_480;  // 矩形 480×480
extern const screen_layout_t LAYOUT_ROUND_480; // 圆形 480
```

**布局代码里禁止写死像素坐标**，一律从配置读。这样换圆屏只改一个结构体。

**LVGL 的具体建议**：
- 用 **flex 布局 + 百分比**，不要用绝对坐标 `lv_obj_set_pos()`
- 状态栏不要贴角，改成**顶部居中一行**（两种屏幕都不会被切）
- 字号用配置里的值，不要写死
- 圆形屏时把 `corner_radius` 设成半径，LVGL 会自动按圆裁剪，
  **但裁剪不等于布局合理**——仍然需要单独用 `LAYOUT_ROUND_480` 调一版
- 圆屏在 LVGL 里可以用 `lv_arc`（圆弧）做能量环，效果比进度条好

**成本估计**：矩形版做完之后，加一版圆形布局约 **1–2 天**（因为有配置层，只改布局代码）。

| 屏 | 名称 | 数据来源 | 联网 | 单屏字数 |
|---|---|---|---|---|
| ① | 待机 · 黄历 | **本地计算** | ❌ 不需要 | 55 |

- 夜间（如 23:00–07:00）只显示 ⑤，降低亮度

## 3. 数据契约（接口定义）

> **这一层和屏幕形状无关**，换圆屏不用改。

### 3.1 黄历（本地计算，不走网络）

固件里算，或者更好：**服务器算好一年的，设备下载后本地查表**（省算力、结果统一）。

```json
{
  "date": "2026-09-20",
  "solarDate": "9月20日",
  "weekday": "星期日",
  "lunarDay": "廿三",
  "lunarMonth": "八月",
  "yearGanZhi": "丙午年",
  "dayGanZhi": "丁酉日",
  "solarTerm": "白露 · 第 13 天",
  "good": ["祭祀", "沐浴", "整手足甲"],
  "bad": ["开市", "动土"],
  "directions": [
    { "label": "喜神", "value": "正西" },
    { "label": "财神", "value": "东北" }
  ],
  "clash": "冲兔煞北"
}
```

**字段规则**：
- `good` 最多 3 条、`bad` 最多 3 条（**这是 480×480 的硬限制，不是内容不够**）
- `lunarDay` 是视觉主角，建议 ≥ 96px
- 全量一年数据约 365 × 300 字节 ≈ **110 KB**，可以整年缓存在 Flash

### 3.2 今日（服务器每日推送）

```json
{
  "date": "2026-09-20",
  "energyWord": "收",
  "energyLine": "适合收尾，不适合开新事。",
  "bodyReminder": "下午晚些时候能量容易走低，3–4 点休息十分钟。",
  "favorableDirection": "东北 — 适合对话、计划、和安静的决定。",
  "luckyColor": "深蓝",
  "week": [
    { "label": "一", "value": 72, "word": "良" },
    { "label": "二", "value": 78, "word": "良" },
    { "label": "三", "value": 85, "word": "旺" },
    { "label": "四", "value": 68, "word": "平" },
    { "label": "五", "value": 55, "word": "低" },
    { "label": "六", "value": 45, "word": "低" },
    { "label": "日", "value": 60, "word": "平" }
  ],
  "weekLine": "周三最旺，周五周六留力。",
  "chapter": {
    "phase": "责任扩大期",
    "daxian": "32-41 岁",
    "yearIndex": 1,
    "advice": "今年不宜盲目扩张，先处理健康和家庭责任。"
  }

```

**注意**：`energyWord` 严格要求 1 个字，`energyLine` ≤ 16 字。
**这是内容侧的约束**——写文案的人必须遵守，否则屏幕排不下。

### 3.3 语音（按次，上云）

```
设备 → 服务器：POST /api/ask
  { "deviceId", "question" (识别后文本), "contextYear", "contextDimension" }
服务器 → 设备：{ "answer": "..." }
```

**成本控制**（重要）：
- 唤醒词识别**在本地**（ESP-SR），不产生费用
- 只有真正提问才上云
- 服务端记录每日次数，超过额度返回提示（见 §7）

## 4. 分层结构（这样做才能换屏幕）

```
┌─────────────────────────────────────┐
│  数据层：黄历数据 / 今日推送 / 语音     │  ← 与屏幕形状无关
├─────────────────────────────────────┤
│  业务层：日期计算、缓存、额度校验       │  ← 与屏幕形状无关
├─────────────────────────────────────┤
│  排版层：字号、边距、每屏放几行         │  ← 只有这一层受屏幕形状影响
├─────────────────────────────────────┤
│  渲染层：LVGL 对象                    │
└─────────────────────────────────────┘
```

**给开发同学的硬要求**：

1. **禁止在渲染代码里写死坐标和字号**，一律从 `screen_layout_t` 读（见 §0.4）
2. **每屏一个独立函数**（`render_almanac()` / `render_today()` / …），
   这样一个屏幕换布局不影响其他屏
3. **内容由数据驱动**：文案来自 JSON，不要硬编码在 C 代码里
   （否则改文案要重新烧固件）

## 5. 中文字库（**最容易上线才发现的问题**）

### 5.1 三个必须做的事

1. **字库必须覆盖黄历用字**。黄历有大量生僻字：「祭祀」「沐浴」「碓磨」「纳畜」「整手足甲」「冲煞」……
   如果裁剪字库时漏了，屏幕上会出现**豆腐块（缺字方框）**。
2. **上线前跑一遍全量检测**：把**全年 365 天**的黄历内容 + 所有今日文案，
   逐字检查是否在字库里。这个检查脚本必须有。
3. **注意字体授权**：商用字体需要授权。
   **屏幕上不放字体文件、只放"实际用到的字的点阵"** 是常见的合规做法，
   但仍需确认授权条款（建议用开源字体，如思源黑体 / 阿里巴巴普惠体）。

### 5.2 体积估算（决定要不要外挂 Flash）

| 方案 | 大小估算 |
|---|---|
| 全字库（GB2312 常用 6763 字）16×16 点阵 | 约 **220 KB** |
| 全字库 24×24 | 约 500 KB |
| 只取"黄历 + 文案"实际用字（估计 1500–2500 字）24×24 | 约 **110–180 KB** |

**ESP32-S3 通常带 8 MB Flash，放得下**，但要点阵数据放 Flash（不要放 RAM），
按需渲染，避免占用运行内存。

## 6. 语音方案（ESP-SR）

| 环节 | 位置 | 说明 |
|---|---|---|
| **唤醒词识别** | **本地**（ESP-SR） | 免费、即时、断网可用；**这是成本控制的关键** |
| 录音上传 | 设备 → 服务器 | 唤醒后才开始，隐私上也好解释 |
| 语音转文字 | 云端 | 按次计费 |
| 生成回答 | 云端 | 按次计费 |
| 语音合成 | 云端或设备端 | 云端效果好、设备端省钱 |

**唤醒词**：可自定义（用 [esp-sr-model-tool](https://github.com/KiWi233333/esp-sr-model-tool)），
建议做「**陈老师**」——品牌绑定，比"你好小智"更有意义。

**要拿到三个数字**（这是原型阶段的真正目标）：
1. 中文唤醒率（安静环境 / 有噪声环境）
2. 一轮问答的端到端延迟（说话结束 → 开始播放回答）
3. **每次交互的云端成本**

**隐私设计**：本地唤醒 = "没被唤醒就不上传"，
这条要写进产品说明和隐私政策，是麦克风常开设备最重要的合规话术。

## 7. 服务额度与降级（对应商业模型）

| 层 | 是否需要服务授权 |
|---|---|
| ① 黄历、⑤ 极简待机 | **不需要**——服务到期也照常显示 |
| ② 今日、③ 未来 7 天 | 需要（缓存 7 天，断网也能撑一周） |
| ④ 语音 | 需要，且**按日限量**（建议 3–5 次/天） |

**到期后的行为**（必须优雅，不能变砖）：
- 黄历屏**一切照常**
- 今日屏退化为通用内容（不个性化）
- 语音不可用
- 屏幕上**加一行小字**提示，绝不全屏弹窗、绝不遮挡黄历

**授权校验**：
- 本地保存到期时间，断网也能判断
- 联网时与服务器校准
- **给 7 天宽限期**，避免网络异常时误降级

## 8. 验收标准（做完怎么算过）

| 项 | 标准 |
|---|---|
| 五屏渲染 | 与模拟器 `/ambient/` 视觉一致（字号、配色、留白） |
| 黄历准确性 | 日干支、农历日与权威万年历对照，**连续 30 天无差错** |
| 字数约束 | 任何屏幕实际渲染**不超过 80 字、不超过 7 行** |
| 缺字检测 | 全年 365 天内容 + 全部文案，**0 个缺字** |
| 唤醒率 | 安静环境 ≥ 90%，有噪声 ≥ 75%（待实测确定） |
| 延迟 | 一轮问答 ≤ 3 秒 |
| 断网行为 | 黄历照常可用；今日屏用缓存；不报错、不白屏 |
| 到期降级 | 黄历照常、今日退化、语音不可用、有一行提示 |
| 常亮稳定 | 连续运行 7 天不重启、不内存泄漏 |

## 9. 给开发同学的开工顺序（建议）

1. **先跑通屏幕**：LVGL 显示黄历一屏，用**假数据**。这一步最容易踩字体和排版的坑。
2. **接黄历数据**：本地计算或下载整年表，做缺字检测脚本。
3. **加联网**：拉今日数据，做 7 天缓存与断网降级。
4. **加唤醒**：ESP-SR 跑通唤醒词，先只点亮一个灯，不接云端。
5. **接语音问答**：走通一轮完整问答，测延迟和成本。
6. **加轮播与夜间模式**：把它变成一个"会自己待着的物件"。
7. **最后做授权**：额度、到期降级。

> **顺序很重要**：前两步做完，就已经有一个"能看的黄历摆件"了——
> 这本身就是可以拿给人看的东西。后面每一步都是加分项。
> **不要一开始就啃语音**，那是最后一步。

## 10. 还没定、需要产品决定的事

1. **最终屏幕形状**：矩形还是圆形？（见 §0.3，圆形要重做信息架构）
2. **屏幕尺寸**：就是 480×480，还是更小？
   ⚠️ **注意**：圆形屏常见尺寸是 1.28"（240×240）、1.6"（400×400）、2.1"（412×412），
   **大多数圆形屏的实际分辨率比 480×480 小**——如果换圆屏，很可能同时要面对"更小的屏"。
   这一点要一起考虑。
3. **唤醒词**用什么？（建议「陈老师」）
4. **语音每天几次**？超出后是"明天再来"还是可充值？
5. **黄历口径**采用哪一家？（宜忌各家不一致，见硬件评估 §3.2.3）
6. **是否外挂 Flash**：字库 + 整年黄历数据需不需要独立存储芯片？
